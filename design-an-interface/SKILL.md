# 接口设计

基于《软件设计哲学》中的"设计两次"：你的第一个想法不太可能是最好的。生成多种截然不同的设计方案，然后比较。

## 工作流程

### 1. 收集需求并说明问题空间

在设计之前，理解：

- [ ] 这个模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 主要操作是什么？
- [ ] 有什么约束？（性能、兼容性、现有模式）
- [ ] 什么应该隐藏内部 vs 暴露？

询问："这个模块需要做什么？谁会使用它？"

然后，在启动子代理之前，为选定的模块写一份面向用户的问题空间说明：

- 任何新接口都必须满足的约束
- 它将依赖的依赖项及其性质（进程内、可本地替代、远程但自有、真正外部）
- 一份粗略的示意代码草图，用来把约束具体化——不是提案，只是让约束变得具体的一种方式

把说明展示给用户，然后立即进入第 2 步。用户阅读和思考的同时，子代理并行工作。

### 2. 生成设计（并行子代理）

通过宿主提供的子代理机制（如 Task/task）同时生成 3+ 个子代理；宿主不支持子代理时顺序生成。每个必须产生**截然不同**的方法。

```
每个子代理的提示模板：

设计接口：[模块描述]

需求：[收集的需求]

此设计的约束：[为每个代理分配不同的约束]
- 代理 1："最小化方法数量 — 最多 1-3 个方法"
- 代理 2："最大化灵活性 — 支持多种用例"
- 代理 3："针对最常见情况进行优化"
- 代理 4："从 [特定范式/库] 获取灵感"

输出格式：
1. 接口签名（类型/方法/参数，外加不变量、顺序、错误模式）
2. 使用示例（调用者如何使用）
3. 此设计在接缝后隐藏了什么
4. 依赖策略和适配器（各依赖放在接缝哪一侧、跨接缝依赖如何适配）
5. 此方法的权衡
```

### 3. 展示设计

展示每个设计：

1. **接口签名** - 类型、方法、参数
2. **使用示例** - 调用者在实践中如何实际使用
3. **隐藏的内容** - 保持内部的复杂性

按顺序展示设计，以便用户在比较之前吸收每种方法。

### 4. 比较设计

展示所有设计后，参考《软件设计哲学》的相关原则从以下方面比较：

- **接口简洁性**：方法越少、参数越简单 = 越容易学习和正确使用
- **通用性**：无需更改即可处理未来用例；但要警惕过度通用化
- **实现效率**：接口形状是否允许高效实现，还是强制内部实现别扭？
- **深度**：小接口隐藏重大复杂性 = 深模块（好）；大接口薄实现 = 浅模块（避免）
- **易于正确使用 vs 易于误用**：哪种设计更容易被正确使用？

用散文而非表格讨论权衡。突出设计分歧最大的地方。

比较之后，给出你自己的明确推荐：你认为哪个设计最强、为什么。如果不同设计中的元素能很好地结合，提出一个混合方案。要有立场：用户想要一个明确的判断，而不是一份菜单。

### 5. 综合

通常最佳设计结合了多种方案的见解。询问：

- "哪种设计最符合您的主要用例？"
- "其他设计中有哪些元素值得借鉴？"

## 反模式

- 不要让子代理产生相似的设计 — 强制要求截然不同
- 不要跳过比较 — 价值在于对比
- 不要实现 — 这纯粹是关于接口形状
- 不要基于实现难度来评估
