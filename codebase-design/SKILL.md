# 代码库设计

设计**深层模块**：大量行为隐藏在小接口之后，放在干净的接缝处，通过该接口可测试。无论在哪里设计或重构代码，都使用这套语言和这些原则。目标是调用者的杠杆效应、维护者的局部性，以及所有人的可测试性。

## 术语表

准确使用这些术语：不要替换为"组件""服务""API""边界"。一致的语言是全部要点。

**模块**：任何具有接口和实现的东西。刻意与规模无关：可以是函数、类、包或跨越层级的切片。_避免_：单元、组件、服务。

**接口**：调用者正确使用模块所必须知道的一切：类型签名，还包括不变量、顺序约束、错误模式、所需配置和性能特征。_避免_：API、签名（太窄——它们只指类型层面的表面）。

**实现**：模块内部的东西，即它的代码主体。与**适配器**不同：一个东西可以是小适配器、大实现（一个 Postgres 仓库），也可以是大适配器、小实现（一个内存伪造实现）。当主题是接缝时用"适配器"；否则用"实现"。

**深度**：接口上的杠杆效应。调用者（或测试）每学习一单位接口所能使用的行为量。当一个模块把大量行为放在小接口之后时，它是**深**的；当接口几乎与实现一样复杂时，它是**浅**的。

**接缝**（_Michael Feathers_）：一个可以在不原地编辑的情况下改变行为的地方；**模块**的接口所在的*位置*。接缝放在哪里本身就是一项设计决策，与它背后放什么不同。_避免_：边界（与 DDD 的限界上下文重载）。

**适配器**：在接缝处满足接口的具体事物。描述的是*角色*（填哪个槽位），而不是实质（里面是什么）。

**杠杆效应**：调用者从深度中获得的东西。每学习一单位接口就获得更多能力。一份实现在 N 个调用点和 M 个测试中得到回报。

**局部性**：维护者从深度中获得的东西。变更、缺陷、知识和验证集中在一个地方，而不是散布到各个调用者。修复一次，处处修复。

## 深与浅

**深层模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅层模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计接口时，问：

- 我能减少方法数量吗？
- 我能简化参数吗？
- 我能把更多复杂性藏在内部吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深层模块内部可以由小的、可 mock、可替换的部分组成；它们只是不属于接口。模块可以有**内部接缝**（对其实现私有，供自己的测试使用），也可以有接口处的**外部接缝**。
- **删除测试。** 想象删除这个模块。如果复杂性消失，它只是一个直通模块。如果复杂性在 N 个调用者中重新出现，它就在赚取自己的位置。
- **接口就是测试表面。** 调用者和测试穿过同一个接缝。如果你想测试*越过*接口，这个模块多半形状不对。
- **一个适配器意味着假设的接缝。两个适配器才意味着真实的接缝。** 除非确实有东西在接缝两侧变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试自然：

1. **接受依赖，而不是创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 方法越少 = 需要的测试越少。参数越少 = 测试设置越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它向调用者和测试呈现的表面）。
- **深度**是**模块**的属性，相对于它的**接口**来衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**处并满足**接口**。
- **深度**为调用者产生**杠杆效应**，为维护者产生**局部性**。

## 已否定的框架

- **把深度当作实现行数与接口行数的比率**（Ousterhout）：这会奖励灌水实现。我们改用"深度即杠杆效应"。
- **把"接口"当作 TypeScript 的 `interface` 关键字或类的公开方法**：太窄——这里的接口包括调用者必须知道的一切事实。
- **"边界"**：与 DDD 的限界上下文重载。请说**接缝**或**接口**。
