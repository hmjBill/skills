# 深化

如何在给定依赖的情况下安全地深化一簇浅层模块。假定你已掌握 [SKILL.md](SKILL.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

评估深化候选时，对其依赖分类。类别决定深化后的模块如何跨接缝测试。

### 1. 进程内（in-process）

纯计算、内存状态、无 I/O。总是可以深化：合并模块，直接通过新接口测试。不需要适配器。

### 2. 本地可替代（local-substitutable）

有本地测试替身的依赖（如 Postgres 的 PGLite、内存文件系统）。替身存在就可以深化。深化后的模块在测试套件中让替身运行来测试。接缝是内部的；模块的外部接口上没有端口。

### 3. 远程但自有（端口与适配器）

你自己的服务，跨越网络边界（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深层模块拥有逻辑；传输作为**适配器**注入。测试使用内存适配器。生产使用 HTTP/gRPC/队列适配器。

建议的形式：_"在接缝处定义端口，为生产实现 HTTP 适配器，为测试实现内存适配器，这样即使跨网络部署，逻辑也位于一个深层模块中。"_

### 4. 真正外部（mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖作为注入端口；测试提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着假设的接缝。两个适配器才意味着真实的接缝。** 除非至少有理由存在两个适配器（通常是生产 + 测试），否则不要引入端口。单适配器的接缝只是间接层。
- **内部接缝与外部接缝。** 一个深层模块可以有内部接缝（对其实现私有，供自己的测试使用），也可以有接口处的外部接缝。不要仅仅因为测试使用内部接缝就把它们暴露到接口上。

## 测试策略：替换，而不是叠加

- 一旦深化模块接口处的测试存在，浅层模块上的旧单元测试就成了废物；删除它们。
- 在深化模块的接口处编写新测试。**接口就是测试表面**。
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应当经受住内部重构，因为它们描述的是行为，不是实现。如果实现变化时测试必须修改，说明它在测试接口之外的东西。
