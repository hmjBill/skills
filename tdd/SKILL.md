# 测试驱动开发

TDD 就是红 → 绿循环。本技能是这个循环的参考，让它产出值得保留的测试：什么是好测试、测试写在哪里、有哪些反模式，以及循环的规则。每个部分在每一轮循环中都适用：在循环之前和循环进行中查阅，而不是循环之后。

探索代码库时，阅读 `GLOSSARY.md`（如果存在），让测试名称和接口词汇匹配项目的领域语言，并尊重你触及区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该。好测试读起来像规格说明："用户可以用有效购物车结账" 准确告诉你存在什么能力；它能在重构中存活，因为它不关心内部结构。

示例见 [tests.md](tests.md)，模拟指南见 [mocking.md](mocking.md)。

## Seam：测试写在哪里

**Seam** 是你据以测试的公共边界：无需伸手进内部就能观察行为的接口。测试住在 seam 上，绝不针对内部。

**只在预先商定的 seam 上写测试。** 写任何测试之前，写下要测试的 seam 并与用户确认。不要在任何未经确认的 seam 上写测试。你不可能测试一切，因此事先商定 seam，才能让测试工作落在关键路径和复杂逻辑上，而不是每一个边界情况。

问："公共接口是什么，我们应该测试哪些 seam？"

当这个接口的形态本身存疑时（模块有多深、seam 该放在哪里、接口应该暴露什么），加载 `codebase-design` 技能获取词汇。它是模块、接口、深度、seam、适配器、杠杆（leverage）和局部性（locality）等术语的共同来源；它是供查阅的参考，而不是要运行的会话。

## 反模式

- **耦合实现**：mock 内部协作者、测试私有方法，或通过旁路验证（查询数据库而不是使用接口）。识别信号：重构时测试失败，但行为没有改变。
- **Tautological（同义反复）**：断言以代码计算期望值的同样方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`，手工按同样方式推导的快照，断言常量等于自身），因此它按构造通过，永远不可能与代码产生分歧。期望值必须来自独立的事实来源：已知正确的字面量、手工演算过的示例、规格说明。
- **水平切片**：先写所有测试，再写所有实现。批量测试验证的是*想象的*行为：你测试的是事物的*形态*，而不是用户面向的行为；测试对真实变化变得不敏感；在理解实现之前，你就承诺了测试结构。改用**垂直切片**：一次测试 → 一次实现 → 重复，每个测试都是一发 **tracer bullet**，响应上一轮循环教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写足够的代码让它通过。不要预测未来的测试，也不要添加投机性功能。
- **一次一个 slice。** 每个循环一个 seam、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于审查阶段（参见 `review` 技能），而不是红 → 绿实现循环。
