# 代码审查

对 `HEAD` 与用户提供的固定点之间的差异进行双轴审查：

- **标准** — 代码是否符合此仓库的文档化编码标准？
- **规范** — 代码是否忠实地实现了原始 issue / PRD / 规范？

两个轴作为**并行子代理**运行，因此它们不会相互污染上下文，然后此技能聚合它们的发现。

问题追踪器应该已经提供给您——如果 `docs/agents/issue-tracker.md` 缺失，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定点

无论用户说的是什么作为固定点——一个 commit SHA、分支名、tag、`main`、`HEAD~5` 等。不要固执己见；直接传递。如果他们没有指定，问："针对什么审查——分支、commit 还是 `main`？" 在您获得它之前不要继续。

一次性捕获 diff 命令：`git diff <fixed-point>...HEAD`（三个点，以便比较针对合并基础）。也通过 `git log <fixed-point>..HEAD --oneline` 记下提交列表。

### 2. 识别规范源

按此顺序查找原始规范：

1. Commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流程获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 PRD/规范文件。
4. 如果什么都没找到，问用户规范在哪里。如果他们说没有，**规范**子代理将跳过并报告"无规范可用"。

### 3. 识别标准源

仓库中记录代码应该如何写的任何内容。常见位置：

- `CLAUDE.md`、`AGENTS.md`
- `CONTRIBUTING.md`
- `CONTEXT.md`、`CONTEXT-MAP.md`、每个上下文的 `CONTEXT.md` 文件
- `docs/adr/`（架构决策是标准）
- `.editorconfig`、`eslint.config.*`、`biome.json`、`prettier.config.*`、`tsconfig.json`（机器强制的标准——记下它们，但不要重新检查工具已经检查的内容）
- 任何在仓库根目录或 `docs/` 下的 `STYLE.md`、`STANDARDS.md`、`STYLEGUIDE.md` 或类似文件

收集文件列表。**标准**子代理将读取它们。

### 4. 并行生成两个子代理

发送带有两个 `Agent` 工具调用的单个消息。对两者都使用 `general-purpose` 子代理。

**标准子代理提示** — 包含：

- 完整的 diff 命令和提交列表。
- 您在步骤 3 中找到的标准源文件列表。
- 简报："阅读标准文档。然后阅读 diff。报告——按文件/区块（相关时）——diff 违反文档化标准的每个地方。引用标准（文件 + 规则）。区分硬违规和判断调用。跳过工具强制的任何内容。400 字以内。"

**规范子代理提示** — 包含：

- diff 命令和提交列表。
- 规范的路径或获取的内容。
- 简报："阅读规范。然后阅读 diff。报告：(a) 规范要求但缺失或部分的要求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现看起来错误的要求。为每个发现引用规范行。400 字以内。"

如果规范缺失，跳过规范子代理并在最终报告中注明。

### 5. 聚合

在 `## Standards` 和 `## Spec` 标题下呈现两份报告，原样或轻度清理。**不要**合并或重新排名发现——两个轴是故意分开的，以便用户可以独立看到它们。

以一行总结结束：每个轴的总发现，以及被标记的最严重的单个问题（如果有）。

## 为什么双轴

一个更改可能通过一个轴而未通过另一个：

- 遵循每个标准但实现错误的东西的代码 → **标准通过，规范失败。**
- 正是 issue 要求的但破坏项目约定的代码 → **规范通过，标准失败。**

分开报告可以防止一个轴掩盖另一个。
