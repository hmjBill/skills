# 安全最佳实践

## Overview

此 skill 说明了如何识别当前上下文使用的语言与框架，并从该 skill 的 references 目录中加载与该语言和/或框架相关的安全最佳实践信息。

这些信息（如果存在）可用于编写默认即安全（secure by default）的新代码，或在现有代码中被动检测重大问题，或（在用户要求时）生成漏洞报告并建议修复方案。

## Workflow

此 skill 的第一步是识别你被要求使用的、或在当前项目范围内已存在的所有语言和所有框架。重点关注主要核心框架。通常需要同时识别前端与后端的语言和框架。

然后检查此 skill 的 references 目录，确认是否存在与该语言和/或框架相关的文档。确保读取与具体语言或框架相关的所有参考文件。文件名格式为 `<language>-<framework>-<stack>-security.md`。还应检查是否存在与所用框架无关的 `<language>-general-<stack>-security.md`。

如果处理的是包含前后端的 Web 应用，务必同时检查前端和后端的参考文档！

如果你被要求构建一个同时包含前后端的 Web 应用，但未指定前端框架，也请查看 `javascript-general-web-frontend-security.md`。理解如何同时保障前端与后端安全非常重要。

如果该 skill 的 references 目录中没有相关信息，请基于你对该语言、框架及其常见安全最佳实践的知识进行判断。如果不确定，可尝试在线查找安全最佳实践文档。

之后可按以下几种方式执行。

1. 主要模式：从当前开始直接使用这些信息编写默认即安全的代码。适用于新项目启动或新代码编写场景。

2. 次要模式：在项目开发及为用户编写代码过程中被动检测漏洞。可标记关键或非常重要的漏洞，或明显违反安全指导的重大问题，并告知用户。该被动模式应聚焦高影响漏洞与安全默认配置。

3. 用户可以要求生成安全报告或提升代码库安全性。此时应产出完整报告，说明项目在哪些方面未遵循安全最佳实践指导。报告应进行优先级排序，并按严重性与紧迫性划分清晰章节。随后可开始处理这些问题的修复。见下文 #fixes。

## Workflow Decision Tree

- 如果语言/框架不明确，请检查仓库以确定，并列出证据。
- 如果 `references/` 中存在匹配指导，仅加载相关文件并遵循其说明。
- 如果不存在匹配指导，请评估你是否掌握所选语言和/或框架的通用安全最佳实践；但若被要求生成报告，应告知用户缺少具体指导（仍可生成报告或检测确定性的关键漏洞）。

报告顶部应包含简短的执行摘要。

重要：在报告中引用代码时，务必查找并包含被引用代码的行号。

写完报告文件后，向用户总结主要发现。

并告知用户最终报告写入的位置。

如果你已生成报告，让用户先阅读报告，再询问是否开始执行修复。

如果在被动检测中发现关键问题，通知用户并询问是否需要你修复该问题。

在执行修复时，一次只聚焦一个发现。修复代码应包含简洁清晰的注释，说明新代码依据了哪条具体安全最佳实践，并可附上非常简短的原因，解释为何不按该方式实现会有风险。

始终考虑你计划做出的变更是否会影响用户代码功能，并评估这些变更是否可能导致当前项目行为回归。很多情况下，不安全代码会因其他原因被依赖（这也是其长期存在的原因）。避免破坏用户项目，否则可能导致用户未来不愿继续应用安全修复。相比仓促改动，更应基于项目上下文做出经过充分思考、信息充分的修复。

始终遵循用户配置的常规变更或提交流程。如果进行 git 提交，提交信息应清晰说明该改动用于对齐安全最佳实践。尽量避免把多个无关发现合并到同一次提交中。

始终遵循用户配置的常规测试流程（如有），以确认改动未引入回归。考虑变更可能带来的二阶影响；若存在，应在实施前告知用户。

# 安全最佳实践

以下是适用于几乎任何语言或框架的一些安全编码建议。

### Avoid Using Incrementing IDs for Public IDs of Resources

当为某个资源分配 ID 且该 ID 会暴露在互联网侧使用时，避免使用较小的自增 ID。应改用更长的随机 UUID4 或随机十六进制字符串。这可以防止用户推断资源数量并猜测资源 ID。

### A note on TLS

尽管 TLS 对生产部署很重要，但多数开发工作会在禁用 TLS 的环境下进行，或由范围外的 TLS 代理提供。基于这一点，务必谨慎，不要轻易将“缺少 TLS”直接报告为安全问题。对 “secure” cookie 的使用也应非常谨慎：仅当应用实际运行在 TLS 之上时才应设置。如果在非 TLS 应用中设置（例如本地开发或测试部署），会导致应用异常。可以提供环境变量或其他标志覆盖 secure 设置，使其在生产 TLS 部署前保持关闭。另外应避免建议启用 HSTS。在未充分理解其长期影响时使用 HSTS 风险很高（可能导致重大故障和用户锁定），且通常不推荐用于 codex 所评审项目的范围。
