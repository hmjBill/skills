# 架构改进

发现架构摩擦点并提出**深化机会**：把浅层模块变成深层模块的重构。目标是可测试性和 AI 可导航性。

本命令由项目的领域模型*提供信息*，并建立在共享的设计词汇之上：

- 调用 Skill 工具加载 "codebase-design"，获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆效应**、**局部性**）及其原则（删除测试、"接口就是测试表面"、"一个适配器 = 假设接缝，两个 = 真实接缝"）。在每个建议中准确使用这些术语，不要漂移到"组件""服务""API"或"边界"。
- `GLOSSARY.md` 中的领域语言为好的接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应重新争辩的决策。

## 流程

### 1. 探索

**先定范围再扫描：YAGNI。** 深化模块的回报来自让未来的变更更容易，所以给代码库中最近发生变更的部分额外权重。先决定*看哪里*，再开始看：

- 如果用户指明了方向（某个模块、子系统、痛点），采纳它，跳过下面的推断。
- 否则，回看相当长一段提交历史（`git log --oneline`）找出代码库的热点——反复出现的文件和区域——让这些路径优先吸引你的注意力。如果变更分散、没有明显热点，就扩大范围。

先阅读项目的领域词汇表（`GLOSSARY.md`）和你即将触及区域的任何 ADR。

然后启动一个子代理遍历代码库。不要遵循死板启发式——有机地探索，并记录你在哪里感受到摩擦：

- 在哪里理解一个概念需要在许多小模块之间跳转？
- 哪些模块是**浅层**的——接口几乎与实现一样复杂？
- 哪里提取了纯函数仅仅为了可测试性，但真正的 bug 隐藏在调用方式中（没有**局部性**）？
- 哪些紧耦合模块跨接缝泄漏？
- 代码库的哪些部分未经测试，或通过当前接口难以测试？

对你怀疑是浅层的任何东西应用**删除测试**：删除它会集中复杂性，还是只是移动它？"是的，集中了"就是你想要的信号。

### 2. 以 HTML 报告呈现候选方案

把一份自包含的 HTML 文件写入操作系统临时目录，确保没有任何东西落进仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上是 `%TEMP%`），写入 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到一个新文件。为用户打开它（Linux 上用 `xdg-open <path>`，macOS 上用 `open <path>`，Windows 上用 `start <path>`），并告知绝对路径。

报告使用 **Tailwind（通过 CDN）** 做布局和样式，使用 **Mermaid（通过 CDN）** 绘制关系图、流程图或时序图，凡是图能可靠传达结构的地方都用它。把 Mermaid 与手工制作的 CSS/SVG 视觉混用：关系呈图状（调用图、依赖、时序）时用 Mermaid；想要更编辑性的东西（质量图、剖面图、折叠动画）时用手工 div/SVG。每个候选都配一张 **before/after 可视化**。要视觉化。

对每个候选渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：为什么当前架构造成了摩擦
- **解决方案**：用平实中文描述将会改变什么
- **收益**：用局部性和杠杆效应来解释，以及测试将如何改进
- **Before / After 图**：并排、手工绘制，展示浅层与深化
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，渲染为徽章

报告以 **Top recommendation**（首要推荐）部分结尾：你会先处理哪个候选，为什么。

**领域词汇用 `GLOSSARY.md`，架构词汇用 `/codebase-design`。** 如果 `GLOSSARY.md` 定义了"Order"，请谈论"Order intake 模块"，而不是"FooBarHandler"，也不是"Order 服务"。

**ADR 冲突**：如果候选与现有 ADR 矛盾，只有当摩擦足够真实、值得重新审视该 ADR 时才提出来。在卡片中清楚标记（例如警告提示框：_"与 ADR-0007 矛盾，但值得重新开放，因为…"_）。不要列出每个 ADR 禁止的理论重构。

完整的 HTML 脚手架、图示模式和样式指导见 [HTML-REPORT.md](HTML-REPORT.md)。

还不要提出接口。文件写好后，问用户："你想探索哪一个？"

### 3. 质询循环

一旦用户选定候选，调用 Skill 工具加载 "grill-with-docs"，与他们一起走决策树：约束、依赖、深化模块的形状、接缝后面是什么、哪些测试会保留。

随着决策明确，副作用内联发生；按 `grill-with-docs` 的领域文档纪律保持领域模型最新：

- **根据不在 `GLOSSARY.md` 中的概念命名深化模块？** 把术语加入 `GLOSSARY.md`。文件不存在就惰性创建。
- **在对话中磨砺模糊术语？** 立即更新 `GLOSSARY.md`。
- **用户用有分量的理由拒绝候选？** 提议一个 ADR，框架为：_"要我把这个记录为 ADR，让未来的架构审查不再重复建议它吗？"_ 仅当未来探索者确实需要这个理由以避免重新建议同一件事时才提议；跳过临时理由（"现在不值得"）和不言自明的理由。
- **想探索深化模块的替代接口？** 调用 Skill 工具加载 "codebase-design"，使用其中的"设计两次"（DESIGN-IT-TWICE.md）并行子代理模式。
