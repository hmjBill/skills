# 代码审查

对 `HEAD` 与用户提供的固定点之间的差异进行双轴审查：

- **标准** — 代码是否符合此仓库的文档化编码标准？
- **规范** — 代码是否忠实地实现了原始 issue / PRD / 规范？

两个轴通过宿主提供的子代理机制（如 Task/task）作为**并行子代理**运行，因此不会相互污染上下文；宿主不支持并行时顺序执行。随后此技能聚合两边的发现。

问题跟踪器应已提供给你。如果 `docs/agents/issue-tracker.md` 缺失，先使用 `setup-matt-pocock-skills` 技能生成。

## 流程

### 1. 固定点

无论用户说的是什么——一个 commit SHA、分支名、tag、`main`、`HEAD~5` 等——它就是固定点；不要固执己见，直接使用。如果用户没有指定，问："针对什么审查——分支、commit 还是 `main`？" 得到答案前不要继续。

一次性捕获 diff 命令：`git diff <fixed-point>...HEAD`（三个点，以便比较针对合并基）。也通过 `git log <fixed-point>..HEAD --oneline` 记下提交列表。

继续之前，确认固定点可解析（`git rev-parse --verify <fixed-point>`）且 diff 非空（`git diff --stat <fixed-point>...HEAD` 有输出）。坏 ref 或空 diff 应在这里失败，而不是在两个并行子代理内部。

解析或取 diff 失败时：

- `git rev-parse` 失败通常意味着该 ref 尚未 fetch：先 `git fetch origin <fixed-point>`（或 `git fetch --all --tags`）再重试。
- 浅 clone（`git rev-parse --is-shallow-repository` 返回 `true`）中历史被截断，merge-base 可能不存在；先 `git fetch --unshallow` 或 `git fetch --deepen=<n>` 再重试。
- 仍然失败或 diff 为空：向用户报告并确认固定点是否正确，不要继续生成子代理。

### 2. 识别规范源

按此顺序查找原始规范：

1. Commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流程获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规范文件。
4. 如果什么都没找到，问用户规范在哪里。如果他们说没有，**规范**子代理将跳过并报告"无规范可用"。

### 3. 识别标准源

仓库中记录代码应该如何写的任何内容。常见位置：

- `AGENTS.md`、`CLAUDE.md`
- `CONTRIBUTING.md`
- `GLOSSARY.md`、`GLOSSARY-MAP.md`、每个上下文的 `GLOSSARY.md`（词汇表）
- `docs/adr/`（架构决策是标准）
- `.editorconfig`、`eslint.config.*`、`biome.json`、`prettier.config.*`、`tsconfig.json`（机器强制的标准——记下它们，但不要重新检查工具已经检查的内容）
- 仓库根目录或 `docs/` 下的 `STYLE.md`、`STANDARDS.md`、`STYLEGUIDE.md` 或类似文件

收集文件列表。**标准**子代理将读取它们。

除仓库已记录的内容外，标准轴始终携带下面的**坏味道基线**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没记录也适用。两条规则约束它：

- **仓库标准优先**：文档化的仓库标准永远获胜；当它认可基线上会被标记的写法时，抑制该坏味道。
- **一律是判断题**：每个坏味道都只是带标签的启发式（"可能的 Feature Envy"），绝不是硬违规。与这里任何标准一样，跳过工具已强制的内容。

每个坏味道读作*它是什么* → *怎么修*；对照 diff 匹配：

- **Mysterious Name（神秘命名）**：函数、变量或类型的名字没有揭示它做什么或存什么。→ 重命名；若想不出诚实的名字，说明设计本身有问题。
- **Duplicated Code（重复代码）**：同一逻辑形态出现在变更中的多个 hunk 或多个文件里。→ 抽取共享形态，两边调用。
- **Feature Envy（依恋情结）**：方法访问另一个对象的数据比访问自己的还多。→ 把方法移到它所依恋的数据上。
- **Data Clumps（数据泥团）**：同样的少量字段或参数总是一起出现（一个想诞生的类型）。→ 把它们捆成一个类型，传递该类型。
- **Primitive Obsession（基本类型偏执）**：用基本类型或字符串代替一个值得拥有自己类型的领域概念。→ 给这个概念一个专属的小类型。
- **Repeated Switches（重复的 switch）**：对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 换成多态，或让两处共用一个映射。
- **Shotgun Surgery（霰弹式修改）**：一个逻辑变更迫使 diff 中许多文件零散修改。→ 把一起变化的东西聚到一个模块。
- **Divergent Change（发散式变化）**：一个文件或模块因几个互不相关的原因被修改。→ 拆开，让每个模块只因一个原因变化。
- **Speculative Generality（夸夸其谈通用性）**：为规范没有的需求添加抽象、参数或钩子。→ 删掉；内联回去，直到真实需求出现。
- **Message Chains（过长的消息链）**：调用方不应依赖的长 `a.b().c().d()` 导航。→ 在第一个对象上用单个方法隐藏这段漫游。
- **Middle Man（中间人）**：一个类或函数大多只是往下委托。→ 去掉它，直接调用真实目标。
- **Refused Bequest（被拒绝的遗赠）**：子类或实现者忽略或覆盖了它继承的大部分内容。→ 放弃继承，改用组合。

坏味道条目里的"怎么修"只是审查提示，本技能只报告、不执行修改。要落地修复：行为不变的清理走 `simplify` 技能（它只清理、不改行为）；会改变行为或超出审查范围的重构先另行规划（如 `request-refactor-plan`），不要混进修复提交。

### 4. 并行生成两个子代理

通过宿主提供的子代理机制（如 Task/task）并行启动两个子代理；宿主不支持并行子代理时，在当前上下文按顺序逐个运行两个轴，保持两边发现相互独立。

**标准子代理提示** — 包含：

- 完整的 diff 命令和提交列表。
- 您在步骤 3 中找到的标准源文件列表。
- **步骤 3 的完整坏味道基线**（子代理没有其他途径获得它）。
- 简报："报告——按文件/区块（相关时）——(a) diff 违反文档化标准的每个地方：引用标准（文件 + 规则）；(b) 您发现的任何基线坏味道：说出名字并引用 hunk。区分硬违规与判断题：文档化标准的违反可以是硬违规，但基线坏味道一律是判断题；仓库标准覆盖基线。跳过工具强制的任何内容。400 字以内。"

**规范子代理提示** — 包含：

- diff 命令和提交列表。
- 规范的路径或获取的内容。
- 简报："报告：(a) 规范要求但缺失或部分实现的要求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现看起来错误的要求。为每个发现引用规范原文。400 字以内。"

如果规范缺失，跳过规范子代理并在最终报告中注明。

子代理失败、超时或无法启动时，用相同简报在当前上下文按顺序重试该轴；仍不可行（例如 diff 过大无法处理）就把该轴标记为"未完成"并说明原因，继续另一轴——不要静默丢弃任何一个轴。

### 5. 聚合

在 `## Standards` 和 `## Spec` 标题下呈现两份报告，原样或轻度清理。**不要**合并或重新排名发现——两个轴是故意分开的。

以一行总结结束：每个轴的总发现，以及每个轴内最严重的问题（如果有）。不要跨轴选出唯一赢家——那正是分离双轴要防止的重新排名。

## 为什么双轴

一个更改可能通过一个轴而未通过另一个：

- 遵循每个标准但实现错误的东西的代码 → **标准通过，规范失败。**
- 正是 issue 要求的但破坏项目约定的代码 → **规范通过，标准失败。**

分开报告可以防止一个轴掩盖另一个。
