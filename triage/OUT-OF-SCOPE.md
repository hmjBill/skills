# Out-of-Scope 知识库

仓库中的 `.out-of-scope/` 目录保存被拒绝功能请求的持久记录。它有两个用途：

1. **组织记忆** — 功能为什么被拒绝，这样 issue 关闭后理由不会丢失
2. **去重** — 当新 issue 与先前的拒绝匹配时，技能可以呈现先前的决策，而不是重新争论一遍

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个文件。请求同一件事的多个 issue 归入同一个文件。

## 文件格式

文件应该写得轻松、易读 — 更像一份简短的设计文档，而不是数据库条目。使用段落、代码示例和例子，让理由对第一次看到它的人清晰有用。

```markdown
# Dark Mode

本项目不支持深色模式或面向用户的主题定制。

## Why this is out of scope

渲染管线假定单一调色板，定义在 `ThemeConfig` 中。支持多主题需要：

- 包裹整个组件树的主题上下文 Provider
- 逐组件的主题感知样式解析
- 用户主题偏好的持久化层

这是一项重大的架构变更，与本项目聚焦内容创作的定位不符。主题定制属于
嵌入或再分发产出的下游消费者关心的问题。

```ts
// 当前的 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，在构建时解析
  fonts: FontStack;
}
```

## Prior requests

- #42 — "添加深色模式支持"
- #87 — "无障碍夜间主题"
- #134 — "深色主题选项"
```

### 文件命名

对概念使用简短、描述性的 kebab-case 名称：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应该足够可辨认，让人浏览目录时不用打开文件就知道什么被拒绝了。

### 撰写理由

理由要有实质内容 — 不是"我们不想做这个"，而是为什么。好的理由会引用：

- 项目范围或理念（"本项目聚焦 X；主题定制是下游关注点"）
- 技术约束（"支持这个需要 Y，与我们的 Z 架构冲突"）
- 战略决策（"我们选择用 A 而不是 B，因为……"）

理由应该是持久的。避免引用临时情况（"我们现在太忙了"）— 那些不是真正的拒绝，而是推迟。

## 何时检查 `.out-of-scope/`

分诊期间（步骤 1：收集上下文）读取 `.out-of-scope/` 中的所有文件。评估新 issue 时：

- 检查请求是否匹配已有的 out-of-scope 概念
- 匹配看概念相似度，而不是关键字 — "night theme" 匹配 `dark-mode.md`
- 如果有匹配，呈现给维护者："这与 `.out-of-scope/dark-mode.md` 相似 — 我们之前拒绝过，因为 [理由]。你的看法还一样吗？"

维护者可以：

- **确认** — 新 issue 被追加到现有文件的 "Prior requests" 列表，然后关闭
- **重新考虑** — out-of-scope 文件被删除或更新，issue 继续走正常分诊
- **不同意** — 两个 issue 相关但不同，继续走正常分诊

## 何时写入 `.out-of-scope/`

只有当 **enhancement**（不是 bug）作为 `wontfix` 被*拒绝*时。这对 enhancement PR 与对 issue 完全一样：被拒绝的 PR 也记录在这里，这样同一个请求不会以新代码的形式再次回来。

当某物因**已经实现**而以 `wontfix` 关闭时，**不要**写到这里。那是已构建的功能，不是被拒绝的功能；记录它会用错误的拒绝污染去重检查。此时改为在关闭评论中指向该功能已有的位置。

流程：

1. 维护者决定某个功能请求超出范围
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 如果有：把新 issue 追加到 "Prior requests" 列表
4. 如果没有：创建新文件，包含概念名称、决策、理由和第一个先前请求
5. 在 issue 上发布评论，解释决策并提及该 `.out-of-scope/` 文件
6. 带 `wontfix` 标签关闭 issue

## 更新或删除 out-of-scope 文件

如果维护者对先前拒绝的概念改变主意：

- 删除该 `.out-of-scope/` 文件
- 技能不需要重新打开旧 issue — 它们是历史记录
- 触发重新考虑的新 issue 继续走正常分诊
