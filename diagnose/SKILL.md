# 诊断

处理困难 Bug 的纪律。跳过阶段仅在明确合理时进行。

在探索代码库时，读取项目的领域词汇表（如 `GLOSSARY.md` 或 `docs/adr/`；不存在则跳过）获取相关模块的清晰心智模型，并检查您所涉及区域的 ADR。

## 脱敏

本技能会要求您展示命令、输出和捕获的工件。**首先脱敏所有秘密**：在其位置写 `<REDACTED>`。针对环境变量构建循环，使凭据留在环境中，而不是出现在您展示的内容里。捕获的工件可能带认证头：只引用携带信号的行。

如果脱敏后的输出不足以诊断 Bug，请说明并询问用户。

## 阶段 1 — 构建反馈循环

**这就是技能。** 其他一切都是机械的。如果您有一个**紧凑**的通过/失败信号（能在*这个* Bug 上变红），您将找到原因 — 二分、假设测试和检测都只是消耗该信号。如果您没有信号，再怎么看代码也救不了您。

在这里投入不成比例的努力。**积极主动。发挥创意。拒绝放弃。**

### 构造反馈循环的方法 — 大致按此顺序尝试

1. **针对 Bug 接触点的失败测试** — 单元、集成、端到端。
2. **针对运行中的开发服务器的 curl/HTTP 脚本**。
3. **CLI 调用** 配合 fixture 输入，将 stdout 与已知良好的快照进行比较。
4. **无头浏览器脚本**（Playwright/Puppeteer）— 驱动 UI，对 DOM/console/network 进行断言。
5. **重放捕获的跟踪。** 将真实网络请求/有效载荷/事件日志保存到磁盘；通过隔离的代码路径重放。
6. **临时测试工具。** 启动系统的最小子集（一个服务、带mock的依赖），通过单次函数调用执行 Bug 代码路径。
7. **属性/模糊循环。** 如果 Bug 是"有时输出错误"，运行 1000 个随机输入并寻找失败模式。
8. **二分法工具。** 如果 Bug 出现在两个已知状态之间（提交、数据集、版本），自动化"在状态 X 启动、检查、重复"，以便您可以 `git bisect run` 它。
9. **差异循环。** 通过旧版本 vs 新版本（或两个配置）运行相同输入并比较输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人点击，使用 `scripts/hitl-loop.template.sh` 驱动他们，使循环仍然是结构化的。该脚本需要 bash 环境（Windows 使用 Git Bash 运行）：复制到工作目录、按注释改好步骤后执行；捕获的输出反馈给您。

构建正确的反馈循环，Bug 就 90% 已修复。

### 收紧循环本身

将循环视为产品。一旦您有了一个循环，**收紧**它：

- 我能让它更快吗？（缓存设置、跳过无关初始化、缩小测试范围。）
- 我能让信号更尖锐吗？（对特定症状进行断言，而不是"没有崩溃"。）
- 我能让它更确定性吗？（固定时间、种子 RNG、隔离文件系统、冻结网络。）

30 秒的脆弱循环比没有循环好不了多少；2 秒的确定性循环才够紧凑，是调试超能力。

### 非确定性 Bug

目标不是干净的复现而是**更高的复现率**。循环触发 100×，并行化，增加压力，缩小时间窗口，注入 sleep。约 50% 的偶发（flaky）Bug 是可调试的；1% 则不是 — 不断提高复现率直到可调试。

### 当您真的无法构建循环时

明确停下来并说出来。列出您尝试过的。向用户请求：（a）访问任何能复现它的环境，（b）已脱敏的捕获工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或（c）添加临时生产检测的许可。**没有循环不要继续假设。**

### 完成判据：一个会变红的紧凑循环

阶段 1 的完成标志是循环**紧凑**且**能变红**：您能说出**一条命令**（脚本路径、测试调用、curl），并且您**已经至少运行过它一次**（展示调用及其输出，已脱敏）。这条命令必须：

- [ ] **能变红**：它驱动真实的 Bug 代码路径并断言**用户的确切症状**，因此能在这个 Bug 上变红、修复后变绿。不是"运行而不报错"；它必须能**捕获这个特定 Bug**。
- [ ] **确定性**：每次运行给出相同结论（偶发 Bug：按上文所述，固定且高的复现率）。
- [ ] **快速**：秒级，而非分钟级。
- [ ] **代理可运行**：您可以无人值守地运行它；人在回路中只能通过 `scripts/hitl-loop.template.sh`。

如果您发现自己在命令存在之前就阅读代码构建理论，**停下：直接跳到假设正是本技能要防止的失败。** 没有能变红的命令，就不进入阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。观察它随 Bug 出现而变红。

确认：

- [ ] 循环产生用户描述的失败模式 — 而不是附近恰好出现的不同失败。错误的 Bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或者对于非确定性 Bug，以足够高的速率可调试）。
- [ ] 您已捕获确切症状（错误消息、错误输出、慢计时），以便后续阶段可以验证修复实际解决了它。

### 最小化

一旦变红，将复现裁剪到**仍然会变红的最小场景**。**一次一个**地削减输入、调用者、配置、数据和步骤，每次削减后重新运行循环，只保留对失败起承重作用（load-bearing）的部分。

为什么费这个劲：最小复现会缩小阶段 3 的假设空间（剩余可怀疑的活动部件更少），并成为阶段 5 干净的回归测试。

完成标志是**剩余的每个元素都起承重作用（load-bearing）**：移除其中任何一个都会让循环变绿。

在完成复现**和**最小化之前不要继续。

## 阶段 3 — 假设

在测试任何假设之前生成 **3-5 个排名假设**。单一假设生成会锚定在第一个似是而非的想法上。

每个假设必须是**可证伪的**：说明它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 将使 Bug 消失 / <改变 Z> 将使其恶化。"

如果无法说明预测，假设只是感觉 — 丢弃或打磨它。

**在测试之前向用户展示排名列表。** 他们通常有领域知识可以立即重新排名（"我们刚刚部署了 #3 的更改"），或者知道他们已经排除的假设。廉价检查点，巨大时间节省。如果用户不在，不要阻止 — 如果用户 AFK，请继续您的排名。

## 阶段 4 — 检测

每个探针必须映射到阶段 3 的特定预测。**一次更改一个变量。**

工具偏好：

1. **调试器/REPL 检查** 如果环境支持。一个断点胜过十个日志。
2. **边界处的有针对性日志** 区分假设。
3. 永不"记录一切然后 grep"。

**为每个调试日志添加标签** 使用唯一前缀，例如 `[DEBUG-a4f2]`。最终清理成为单个 grep。带标签的日志存活；标签日志死亡。

**性能分支。** 对于性能回归，日志通常是错误的。相反：建立基线测量（计时工具、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

**在修复之前**编写回归测试 — 但仅当存在**正确的接触点**时。

正确的接触点是测试在调用站点发生时锻炼**真实 Bug 模式**的接触点。如果唯一可用的接触点太浅（单调用者测试而 Bug 需要多个调用者、单元测试无法复制触发 Bug 的链），那里的回归测试会给出虚假信心。

**如果没有正确的接触点存在，那本身就是发现。** 注意它。代码库架构阻止 Bug 被锁定。将其标记到下一阶段。

如果存在正确的接触点：

1. 将最小化的复现变成该接触点的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始（未最小化）场景重新运行阶段 1 反馈循环。

## 阶段 6 — 清理 + 复盘

在宣布完成之前需要：

- [ ] 原始复现不再复现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或者记录了接触点的缺失）
- [ ] 所有 `[DEBUG-...]` 检测已移除（grep 前缀）
- [ ] 临时原型已删除（或移动到明确标记的调试位置）
- [ ] 正确的假设在提交/PR 消息中说明 — 以便下一个调试者学习

**然后问：什么能防止这个 Bug？** 如果答案涉及架构变更（没有好的测试接触点、调用者纠缠、隐藏耦合），请使用具体细节移交到 improve-codebase-architecture skill。在修复之后提出建议，而不是之前 — 您现在拥有比开始时更多的信息。
