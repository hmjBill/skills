# 交互式测验（跨机通用）

把用户手里已有的学习材料变成一轮有反馈的测验，而不是把材料重新讲一遍。
任何电脑、任何宿主（Claude Code、Cursor、Codex 等）都适用：不假设固定的
笔记库目录结构，材料范围由用户指定或现场探测。

## 何时用 / 不用

**用**：用户说「考考我」「测验一下」「帮我巩固 X」，或刚读完一批材料想验证掌握度。

**不用**：

- 用户要系统讲新知识 → 那是教学 / 知识导入的活，先补齐材料再测验
- 用户要批量生成记忆卡 → 走 Anki 类制卡工具（如 AnkiConnect）；两者可接力：
  测验暴露薄弱项 → 再针对性制卡

## 前置条件

无强制依赖，但材料必须当前可读：

- 本地 Markdown / Obsidian 笔记库（含 `.obsidian/` 的目录）
- PDF、网页、教材扫描件的文本层
- 用户直接粘贴或口述的内容

材料还没形成可读文本时先补齐（整理、转录、抽取文本层），再开始测验。
拿不到材料就先问范围，**不要凭空出题**。路径与实际不符时先核对实况再操作。

## 工作流

### 1. 确定范围

- 用户指定主题、目录或具体文件 → 直接用
- 只说主题没说位置 → 在当前工作目录 / 笔记库内检索匹配的笔记，把候选列给用户挑
- 都没说 → 问一句「这次考哪个主题或哪批材料」

### 2. 读材料并建概念清单

提炼可考的东西：定义、原理、流程、参数、对比关系、常见错误。
先定 3–8 个概念作为本轮覆盖范围，**超出这个数量说明范围没收窄**。

### 3. 诊断（可选）

用户自己也不确定底子时，先用 2–3 道基础题试水，再决定起点难度。

### 4. 出题

题型按材料性质选，不硬凑：

- **概念回忆**：「解释 X」→ 对比材料内容评分
- **选择 / 填空**：关键事实与易混点
- **行为预测**：「X 失败时会怎样」
- **对比区分**：「A 和 B 的分界在哪」
- **场景应用**：「Y 场景下怎么用 X」
- **操作 / 代码题**：技术内容给可执行的实际任务

### 5. 评分与反馈

- 三档判定：正确 / 部分正确 / 需要复习
- 每道题都指回原位：Obsidian 用 `[[笔记名]]`，其他材料用 `相对路径:章节`、
  PDF 页码、网页标题 + URL
- 答错时给一段短原文摘录，让用户看见依据，而不是只判对错

### 6. 薄弱项处理

- 同一知识点换个场景再问一次，不要原题重放
- 连续两次错的，明确标成「未掌握」，并说明缺的是哪个环节
- 记录只留在会话内；要落盘（错题文件、复习标记）先出方案等用户确认

### 7. 会话总结

覆盖的概念、各档掌握度、下一轮建议考什么。控制在几行，不复述全部题目。

## 出题纪律（硬规则）

- 题目只能来自材料，不引入材料里没有的事实
- 选项描述中性，**不泄露正确性**，不打「推荐」标记
- 正确答案位置随机，不固定首尾
- 干扰项是该领域真实存在的概念或常见误解，不是明显废选项
- 难度递进：回忆 → 理解 → 应用

详细配比、重问策略与宿主有选择题工具时的排版规范见
`references/quiz-rules.md`。

## 写入边界

- 材料默认只读
- 要写复习标记、错题记录、进度文件：先说明写哪些文件、加什么字段，等用户确认
- 用户库已有自己的字段 / 模板规范时按库规范来，不另行发明一套追踪体系

## 反模式

- 把测验做成打分秀：目标是暴露盲点，不是让用户舒服或难受
- 一错就把整章重讲一遍：只补错的那一点，然后换角度再问
- 用材料外的通用知识「补充」题目：超出范围的题一律不出
