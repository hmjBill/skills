# 接口设计

基于《软件设计哲学》中的"设计两次"：你的第一个想法不太可能是最好的。生成多种截然不同的设计方案，然后比较。

## 工作流程

### 1. 收集需求

在设计之前，理解：

- [ ] 这个模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 主要操作是什么？
- [ ] 有什么约束？（性能、兼容性、现有模式）
- [ ] 什么应该隐藏内部 vs 暴露？

询问："这个模块需要做什么？谁会使用它？"

### 2. 生成设计（并行子代理）

使用 Task 工具同时生成 3+ 个子代理。每个必须产生**截然不同**的方法。

```
每个子代理的提示模板：

设计接口：[模块描述]

需求：[收集的需求]

此设计的约束：[为每个代理分配不同的约束]
- 代理 1："最小化方法数量 — 最多 1-3 个方法"
- 代理 2："最大化灵活性 — 支持多种用例"
- 代理 3："针对最常见情况进行优化"
- 代理 4："从 [特定范式/库] 获取灵感"

输出格式：
1. 接口签名（类型/方法）
2. 使用示例（调用者如何使用）
3. 此设计在内部隐藏了什么
4. 此方法的权衡
```

### 3. 展示设计

展示每个设计：

1. **接口签名** - 类型、方法、参数
2. **使用示例** - 调用者在实践中如何实际使用
3. **隐藏的内容** - 保持内部的复杂性

按顺序展示设计，以便用户在比较之前吸收每种方法。

### 4. 比较设计

展示所有设计后，从以下方面比较：

- **接口简洁性**：方法越少、参数越简单 = 越容易学习和正确使用
- **通用 vs 专用**：灵活性 vs 专注
- **实现效率**：形状是否允许高效的内部实现？
- **深度**：小接口隐藏重大复杂性（好）vs 大接口薄实现（坏）
- **易于正确使用** vs **易于误用**

用散文而非表格讨论权衡。突出设计分歧最大的地方。

### 5. 综合

通常最佳设计结合了多种方案的见解。询问：

- "哪种设计最符合您的主要用例？"
- "其他设计中有哪些元素值得借鉴？"

## 评估标准

来自《软件设计哲学》：

**接口简洁性**：方法越少、参数越简单 = 越容易学习和正确使用。

**通用性**：无需更改即可处理未来用例。但要警惕过度通用化。

**实现效率**：接口形状是否允许高效实现？还是强制内部实现别扭？

**深度**：小接口隐藏重大复杂性 = 深模块（好）。大接口薄实现 = 浅模块（避免）。

## 反模式

- 不要让子代理产生相似的设计 — 强制要求截然不同
- 不要跳过比较 — 价值在于对比
- 不要实现 — 这纯粹是关于接口形状
- 不要基于实现难度来评估
