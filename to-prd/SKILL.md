# 功能需求文档（PRD）

产出落在**当前仓库**，不写 AI-Wiki。

## 何时用

- 新功能，行为和边界还没说清
- 需求变更，需要一份能对照的文本
- 要交给别人实现，或要派给子代理

不适用：单行修复、纯重构、纯文档改动。

## 落位与命名

```
docs/prd/<feature-slug>.md      # 一个功能一个文件，kebab-case
```

- 同名文件已存在：追加 `## 变更记录` 段，保留旧内容与日期，**不覆盖**
- 不额外建索引；确实需要时用一个可选的 `docs/prd/README.md`

## 与 GOAL.md 的分工

| 文档 | 回答什么 | 粒度 |
| --- | --- | --- |
| `GOAL.md` | 这个项目要做成什么、明确不做什么 | 项目级 |
| `docs/prd/*.md` | 这个功能具体怎么表现 | 功能级 |

冲突时以 `GOAL.md` 为准，并在 PRD 里写明覆盖原因。

## 写之前：先定测试 seam

先确定在哪个接缝上验证这个功能，再动笔。

- 优先复用既有 seam，不新建
- 能选高就不选低
- 全库 seam 越少越好

seam 定不下来，说明需求还没想清，先回去澄清，不要硬写。

## 结构

八段，模板见 [references/prd-template.md](references/prd-template.md)：

问题 / 方案 / 用户故事 / 行为与边界 / 实施决策 / 测试决策 / 验收判据 / 范围外

## 硬规则

- 每条行为标 `已确认` 或 `AI 假设`；未确认的不得写成"必须"
- 验收判据必须可判定（指向命令或可观察结果）；写不出就标 `待定`，并写清"需要什么才能判"
- 引用既有代码用路径，不复制代码段
- 不写实现细节（那是 ADR / 技术文档的事）
- 不写 Wiki 专用字段（frontmatter、双链、导航表），那些属于 Wiki 侧
- **PRD 进 git**：它是仓库内容，不是本地账本（对比 `PLANS.md` 不进 git）

## 完成后

1. 报告文件路径，以及八段是否齐全
2. 列出仍为 `AI 假设` 或 `待定` 的条目
3. 需要长期沉淀时，提示用户在 AI-Wiki 写一段摘要并链接到该文件；Coding Agent 不直接写 Wiki
