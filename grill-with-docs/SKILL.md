# 拷问并同步文档

对这个方案进行一次不留情面的访谈，直到我们达成共同理解；过程中把术语和关键决策写进仓库。

把方案视为一棵**设计树**：每个决策都会分出新决策。**前沿（frontier）** 是所有前置条件已确定、现在就能问的问题。**一轮**问完当前前沿的全部问题，然后等待回答；不要一次只问一个，也不要把所有问题一次性倒出来。

如果用户明确要求一次只问一个，就退回单问模式，但每个问题仍要附建议答案。

## 提问格式

每轮按以下格式，编号并给出你的建议答案：

```
**Q1** - **<问题标题>**：<问题正文，可包含多个段落或选项>

**建议：** <你的建议答案>

---

**Q2** - **<问题标题>**：...
```

措辞要让用户回答“是”就等于接受你的建议。用户可以直接按编号回答：“1 是，2 选第二个，3 否，因为……”。

同一轮中的问题不能互相依赖。若 Q2 的答案取决于 Q1，Q2 属于下一轮。用户答完一轮后，重新计算前沿，再问下一轮。

## 事实与决策

- **事实由你负责查。** 能通过读代码、查文件或运行命令回答的，不要问用户。需要广泛搜索时派子代理去查。
- **研究不阻塞整轮。** 只有依赖该事实的问题留到下一轮，其余问题现在就问。
- **决策由用户负责。** 不要替用户回答，也不要因为“看起来显然”就跳过。

## 结束条件

当前沿为空——每条分支都走过、没有留下默认假设——访谈结束。此时停下，明确问用户是否已达成共同理解。**在用户确认之前，不要开始实现、修改代码，或写方案之外的文件。**

如果用户中途叫停，以已确认的内容为准，并列出仍未解决的决策。

## 领域意识

在探索代码库时，还要查找现有文档：

### 文件结构

大多数仓库有一个单一上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，则该仓库有多个上下文。地图指向每个上下文的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统范围的决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 上下文特定的决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

惰性创建文件——只有在有内容要写时才创建。如果不存在 `GLOSSARY.md`，则在第一个术语被解决时创建一个。如果不存在 `docs/adr/`，则在需要第一个 ADR 时创建它。

## 会话期间

### 对照词汇表挑战

当用户使用的术语与 `GLOSSARY.md` 中的现有语言冲突时，立即指出。"你的词汇表将 'cancellation' 定义为 X，但你似乎指的是 Y——到底是哪个？"

### 锐化模糊语言

当用户使用模糊或重载的术语时，提出精确的规范术语。"你说的是 'account'——你指的是 Customer 还是 User？这些是不同的东西。"

### 讨论具体场景

当讨论领域关系时，用具体场景对它们进行压力测试。设计探测边缘情况的场景，迫使参与者对概念之间的边界保持精确。

### 与代码交叉引用

当用户说明某事如何工作时，检查代码是否同意。如果你发现矛盾，将其暴露出来："你的代码取消整个 Orders，但你刚才说部分取消是可能的——哪个是正确的？"

交叉核对的范围是代码、`GLOSSARY.md` 和 ADR；issue tracker 或聊天记录里的历史讨论不会自动进入视野，必要时向用户说明这一点。

### 内联更新 GLOSSARY.md

当一个术语被解决时，就在当时更新 `GLOSSARY.md`。不要批量处理——捕捉它们发生时的情况。使用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md) 中的格式。

`GLOSSARY.md` 应完全不含实现细节。不要将 `GLOSSARY.md` 当作 spec、草稿本或实现决策的存放处——它只是术语表，仅此而已。只收录对领域专家有意义的术语。

它应该经常变短，而不只是变长：合并同义词、修正或删除不再准确的条目，比不断追加更重要。

### 谨慎提供 ADR

只有当三个条件都满足时才提供创建 ADR：

1. **难以逆转**——以后改变想法的代价是显著的
2. **没有上下文会令人惊讶**——未来的读者会想知道"为什么他们这样做？"
3. **真正权衡的结果**——存在真正的替代方案，你出于特定原因选择了其中一个

如果三个条件中缺少任何一个，跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
